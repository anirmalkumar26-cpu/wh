A thread in an operating system is the smallest unit of execution that can be scheduled by the operating system. A process is a program in execution, and a thread represents an individual path of execution within that process. A process may contain a single thread or multiple threads. When a process contains multiple threads, it is called a multithreaded process. Threads are an important concept in modern operating systems because they allow programs to perform multiple activities concurrently and, on multicore processors, in parallel.

To understand threads clearly, it is important to understand the difference between a process and a thread. A process is an independent execution environment that has its own address space and resources. A thread exists inside a process and uses the resources belonging to that process. Each thread has its own program counter, CPU registers, stack, and thread state. However, threads belonging to the same process share the process's code section, global data, heap, address space, and resources such as open files. Because threads share these resources, communication between them can be much faster and easier than communication between separate processes.

Every thread needs its own program counter because different threads can be executing different instructions at the same time. It also needs its own set of CPU registers to store temporary execution information. Each thread has its own stack, which contains function calls, local variables, parameters, return addresses, and other temporary information. The stack cannot normally be shared between threads because each thread can be executing different functions with different local variables. In contrast, the code, global variables, and dynamically allocated memory in the heap are commonly shared by all threads of the same process.

The main purpose of using threads is to allow a program to perform multiple activities concurrently. Consider a web browser. One activity may be handling user input, another may be downloading information from the internet, and another may be displaying or processing webpage content. If all these activities were performed by a single thread, the program might become unresponsive whenever that thread had to wait for an input or output operation. With multiple threads, one thread can wait for network data while another thread continues processing or responding to the user.

Threads are particularly useful for improving responsiveness. In a graphical application, for example, one thread can handle the user interface while another performs a long calculation. If the calculation takes several seconds, the interface can continue responding to the user instead of appearing completely frozen. This makes multithreaded applications more convenient and responsive.

Another important advantage of threads is resource sharing. Threads belonging to the same process share the same address space and many of the same resources. This makes it relatively easy for them to exchange information through shared memory. Separate processes normally require inter-process communication mechanisms to exchange information, while threads can often communicate simply by accessing shared variables or data structures. However, this advantage also introduces problems because multiple threads accessing the same data at the same time can interfere with one another.

Threads can also improve performance on multicore processors. Suppose a computer has four CPU cores and a program has several independent threads. The operating system may schedule different threads on different cores, allowing them to execute at the same time. This is called parallelism. On a single-core processor, multiple threads cannot execute literally at the same instant, but the operating system can rapidly switch between them. This gives the appearance of simultaneous execution and is known as concurrency. Therefore, concurrency means that multiple tasks can make progress during overlapping periods, while parallelism means that multiple tasks are actually executing simultaneously on different processing resources.

The operating system manages threads using information about each thread. This information is commonly maintained in a structure called a Thread Control Block, or TCB. The Thread Control Block contains information such as the thread identifier, current state, program counter, CPU registers, stack information, scheduling information, priority, and a reference to the process to which the thread belongs. The exact structure varies between operating systems, but the purpose is the same: to maintain enough information for the operating system to manage, stop, and later resume the thread.

A thread normally passes through several states during its lifetime. When a thread is first created, it is in the new state. After creation, it may enter the ready state, meaning that it is prepared to execute but is waiting for CPU time. When the scheduler assigns a processor to it, the thread enters the running state. If the thread needs to wait for an input/output operation, a lock, a signal, or another event, it may enter the waiting or blocked state. Once the required event occurs, the thread can return to the ready state. When the thread finishes its execution, it enters the terminated state.

The operating system uses a scheduler to decide which runnable thread should receive CPU time. When the operating system changes the CPU from one thread to another, a context switch occurs. During a context switch, the current execution state of one thread is saved and the execution state of another thread is restored. The saved information can include the program counter, CPU registers, stack pointer, and processor state. Context switching is necessary for multitasking, but it introduces overhead because the processor spends some time saving and restoring execution states rather than performing application work.

Threads can be implemented at the user level or at the kernel level. User-level threads are managed primarily by a user-space library or runtime system. The operating system may not directly schedule each individual user thread. User-level thread management can be very fast because creating and switching between threads may not require as much kernel involvement. However, traditional user-level thread implementations can have problems when a thread performs a blocking operation, because the kernel may not be aware that other user-level threads are ready to execute.

Kernel-level threads are managed directly by the operating system kernel. The kernel knows about these threads and can schedule them individually. If one thread becomes blocked while waiting for input/output, the kernel can schedule another runnable thread. Kernel-level threads also allow different threads to execute on different CPU cores. The disadvantage is that operations involving the kernel generally have more overhead than purely user-space operations.

Different threading models describe how user-level threads are mapped to kernel-level execution contexts. In the many-to-one model, many user threads are mapped to a single kernel thread. This approach can have low overhead, but it cannot provide true parallel execution across multiple cores through that single kernel thread, and blocking can affect the entire group. In the one-to-one model, each user thread corresponds to a kernel thread. This provides good support for parallel execution, but creating a very large number of threads can increase system overhead. The many-to-many model maps many user threads to a number of kernel threads, attempting to combine the flexibility of user-level threads with the parallelism provided by kernel-level execution. The two-level model is similar but can also allow certain user threads to be bound directly to particular kernel threads.

One of the biggest challenges in multithreaded programming is synchronization. Since threads in the same process share memory, two or more threads may access the same variable or data structure at the same time. If their operations are not properly coordinated, the result may be incorrect. A race condition occurs when the outcome of a program depends on the timing or ordering of concurrent operations.

For example, suppose two threads both need to increase a shared counter. The operation of increasing the counter may involve reading its current value, adding one, and storing the new value. If the counter initially contains zero, both threads might read zero before either thread stores its result. Both could then calculate one and store one. Although two increments were requested, the final value could incorrectly be one instead of two. This is a classic race condition.

The portion of a program that accesses shared data and must be protected from conflicting concurrent access is called a critical section. Synchronization mechanisms are used to control access to critical sections. A mutex, or mutual exclusion lock, is one of the most common mechanisms. A thread acquires the mutex before entering the critical section and releases it after finishing. While one thread holds the mutex, another thread attempting to acquire the same mutex must wait.

Semaphores are another important synchronization mechanism. A semaphore maintains a counter and provides operations commonly called wait and signal. A binary semaphore can be used for certain mutual-exclusion purposes, while a counting semaphore can allow a limited number of threads to access a resource at the same time. Condition variables are also commonly used when a thread needs to wait until a particular condition becomes true. Atomic operations provide another method for safely performing certain operations without allowing other threads to observe an incomplete operation.

Synchronization introduces its own problems. One of the most serious is deadlock. Deadlock occurs when two or more threads wait indefinitely for resources held by one another. For example, suppose Thread A holds Lock A and waits for Lock B, while Thread B holds Lock B and waits for Lock A. Neither thread can continue because each is waiting for the other. The four classic conditions associated with deadlock are mutual exclusion, hold and wait, no preemption, and circular wait.

Another problem is starvation. Starvation occurs when a thread waits for an excessively long time because other threads continuously receive the CPU or a required resource. Unlike deadlock, the system as a whole may continue making progress, but a particular thread may be repeatedly denied the opportunity to proceed. Proper scheduling and synchronization policies can help reduce starvation.

Threads are also useful in servers and other high-performance applications. A server may receive many requests from different users. Instead of processing only one request at a time, it can use multiple worker threads. Each worker thread can process a different request, allowing multiple requests to make progress concurrently. Many applications use a thread pool, which is a collection of reusable worker threads. When a task arrives, it is assigned to an available worker instead of creating a new thread for every task. Thread pools reduce the overhead of repeatedly creating and destroying threads and also prevent an application from creating an uncontrolled number of threads.

Thread-local storage is another important concept. Although threads of the same process normally share memory, sometimes each thread needs its own private copy of a particular variable. Thread-local storage provides this capability. Each thread has its own instance of the variable, so changes made by one thread do not directly affect the corresponding variable of another thread.

Threads can be classified according to the kind of work they perform. A CPU-bound thread spends most of its time performing computations, such as mathematical calculations, simulations, or data processing. An I/O-bound thread spends a significant amount of time waiting for input/output operations such as disk access, network communication, or user input. Multithreading can be particularly useful when an application has I/O-bound activities because while one thread is waiting for I/O, another runnable thread can use the processor.

Threads generally have lower creation and management costs than separate processes because threads can share the resources of an existing process. However, this does not mean threads are free. Each thread requires memory for its stack and execution state, and the operating system or runtime must manage scheduling and synchronization. Creating too many threads can actually reduce performance because of increased memory usage, context switching, scheduling overhead, and synchronization costs.

There is also an important difference between thread failure and process failure. Threads share the same process resources, so a serious problem in one thread can potentially affect the entire process. Separate processes generally provide stronger isolation because they normally have separate address spaces. Therefore, processes are often preferred when strong isolation is important, while threads are useful when efficient sharing and communication are more important.

The relationship between processes and threads can therefore be summarized as follows. A process provides the resource environment and address space, while threads provide the execution paths within that environment. A process can contain one or more threads. Threads belonging to the same process share code, data, heap, and many other resources, but each thread maintains its own program counter, registers, and stack.

In conclusion, threads are a fundamental mechanism in modern operating systems for achieving concurrency, responsiveness, resource sharing, and parallel execution. A thread is an independently schedulable execution unit within a process. It has its own execution state but shares many resources with other threads in the same process. Threads make applications more efficient and responsive, especially on multicore systems, but their shared-memory nature introduces challenges such as race conditions, deadlocks, starvation, and synchronization overhead. Understanding thread states, Thread Control Blocks, context switching, user-level and kernel-level threads, multithreading models, synchronization, and thread scheduling provides a strong foundation for understanding how modern operating systems execute multiple activities efficiently.
